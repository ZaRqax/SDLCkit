# Подключение нескольких существующих репозиториев

Клонируйте кит отдельно, например в `~/tools/SDLCkit`. Существующие `billing-api`, `dashboard` и `shared-contracts` оставьте в их каталогах. Общий родительский AGENTS.md не является единственным механизмом: установщик создаёт нужные адаптеры в каждом выбранном проекте и сохраняет пользовательские инструкции.

```bash
cd ~/tools/SDLCkit
./setup.sh --target /workspace/projects --harness codex --dry-run
./setup.sh --target /workspace/projects --harness codex --non-interactive
./setup.sh --target /workspace/projects --doctor
```

Просмотрите обнаруженные проекты, команды, зависимости и предлагаемые изменения. Для репозиториев вне корня явно укажите разрешённые пути в workspace-конфигурации; обход через `..` или symlink не должен расширять область автоматически. Секреты не хранятся в профилях или артефактах.

`workspace.json`/YAML описывает проекты и общие параметры; `project.json`/YAML — реальные команды, генерируемые пути и политику конкретного проекта. Код Python/TypeScript не получает Go Taskfile или микросервисную архитектуру. Интеграции отключены по умолчанию; работа из сообщения или файла не требует Jira/GitHub.

Для задачи на несколько проектов сначала определите граф зависимостей: контракт → сервер → клиент. Независимые задачи можно запускать параллельно только явно и в отдельных git worktree/клонах. Сохраняйте владельцев, ревизии, попытки, проверки и результаты. Затем проверьте общий контракт и подготовьте согласованные локальные артефакты либо отдельно разрешённые PR/MR.

Установка не запускает фоновые процессы и не меняет глобальные hooks. Команды удаления/восстановления используют манифест и сохраняют пользовательские изменения. Подробности: [onboarding.md](onboarding.md), [compatibility.md](compatibility.md), [orchestration.md](orchestration.md) и [INSTALL.md](../INSTALL.md).
